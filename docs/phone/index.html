Operating manual

I have no computer. The phone is the machine.

That is not a limitation to apologise for — it is a constraint that has already produced a 3-star developer tool, two shipped Android apps and a published Termux textbook. This is the system that makes it work.

The phone does

  • Read, write, commit. Every line of code I have shipped was typed on a phone.
  • Git: clone, branch, commit, push, review PRs.
  • gh: the GitHub CLI — issues, PRs, releases, Pages, Actions.
  • Python, Node, shell, a local static server, an editor (nano, or my own).
  • The learning loop: read, attempt, quiz, log.
  • Everything that needs judgement, taste and typing.

The CI runner does

  • npm ci, TypeScript, ESLint, the Next.js static export.
  • Gradle builds and Android release APKs.
  • Docker images and anything else that needs a real Linux userland.
  • Deployments to GitHub Pages, Vercel, Netlify, Render.
  • Every build that needs glibc — because Android is bionic.

The loop

One day, five commands, about an hour

This is the same daily loop as the learning design, sized for a phone. The only difference is that the build is somebody else's job.

01

Pull

cd ~/Study-with-ai && git pull

Ten seconds. Everything else happens against what is already on the server.

02

Attempt first

nano notes/<topic>.md

Write what you think before you ask anything. This is the rule that keeps the AI a tutor and not a crutch.

03

Commit the decision

git add -A && git commit -m "What I decided, not what I changed"

A commit is a dated record of a thought. That is the whole point of Git as memory.

04

Push and let CI build

git push && gh run watch

The build happens on GitHub's Ubuntu runner. You watch it on the phone like a build log.

05

Log the mistake

$EDITOR journal/$(date +%F)-<slug>.md

Attempt, mistake, fix. The one folder an AI agent is never allowed to write.

Known limits

Five things that will bite you, and what to do about them

Found the hard way, so you do not have to.

Native binaries need glibc; Android is bionic

Next.js's Turbopack/SWC, lightningcss and Gradle's native parts are compiled against glibc. On stock Termux they will not load.

Fix · Push the build to GitHub Actions. A workflow file is the build machine. This is exactly the rule AppFlow already states.

You cannot build a big project in 20 minutes between classes

A full Next.js build on a mid-range Android phone is slow, hot, and drains the battery for a result you can get free in CI.

Fix · Never build locally. `git push` is the build command. Watch it with `gh run watch` from the same phone.

/sdcard is not a POSIX filesystem

Android's shared storage breaks permissions, symlinks and case sensitivity. Git and proot both misbehave there.

Fix · Keep the clone in Termux's own home (`~/Study-with-ai`). Clone inside the Ubuntu filesystem too, if you use proot.

A 6-inch screen is a hostile editor

Typing a 200-line TypeScript file on a phone keyboard is slow, and typo-driven commits are a real cost.

Fix · Keep the phone for short, high-leverage edits: READMEs, issues, PR reviews, small fixes. Use an agent for the long writes, and never let it write the journal.

Termux is not on the Play Store

The Play Store build is years old and its package manager is broken.

Fix · Install from F-Droid: f-droid.org/packages/com.termux. Then `pkg update && pkg install git gh`.

Git is the only required habit

Everything else in this system is optional tooling. Committing is the part that makes a phone-only workflow work at all, because the repository is the memory and the remote is the build machine.

One repo, one purpose

AppFlow says it: keep apps small, distinct and time-boxed to four weeks. The same rule applies to repositories. A phone session is 20 minutes — scope accordingly.

Never build on the phone

A local build is slow, hot and useless, because CI will do it faster and for free. The only exception is a five-second type check to catch a typo before you push.
